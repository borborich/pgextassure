root-cause review and, where appropriate, coordinated disclosure.

## What the pilot established

The scanner completed on C, Rust, SQL-heavy, background-worker,
network-capable, and multi-version extension layouts without building,
installing, importing, or executing corpus code.

The 838 records are rule matches at source locations, not 838 independent
defects. The review found three important product-level effects:

1. Repeated routines across versioned upgrade scripts can greatly inflate raw
   location counts. For example, one public-execute rule produced 387 location
   matches but only 95 distinct routine signatures.
2. Several projects generate their final install SQL or control files during
   the build. Scanning source templates alone can therefore report an
   incomplete update graph even when release packages contain the generated
   artifact.
3. Repository-wide scanning and package scanning are different operations for
   monorepositories. The manifest records the package-relative `scan_path`
   explicitly instead of silently excluding unrelated trees.

These are actionable benchmark outcomes: future scanner work should provide
root-cause grouping, an explicit and auditable model for generated artifacts,
and safe multi-root or exclusion handling without following symlinks.

## Interpretation gate

The normalized runner output contains counts and capability categories but no
source excerpts. Before any project-specific security statement is published,
critical and high matches must be:

1. grouped by routine or other root cause;
2. separated into expected capability, actionable defect, likely false
   positive, or unresolved;
3. checked against the packaged artifact rather than only its build template;
4. disclosed privately first if the result may represent a previously
   undisclosed vulnerability.
